# Usability testing

Use when the question is whether people can complete realistic tasks with an interface or prototype.

Observe behaviour. Do not teach the interface before testing comprehension. Do not ask participants to predict behaviour when the task can be observed.

## Task writing

- One goal per task
- Use the participant’s language, not implementation names, unless the label itself is under test
- State the outcome, not the click path
- Include starting context (who they are, what they already did)
- Note success criteria before the session

## During the session

- Think-aloud is optional. Silence is data.
- Neutral probes: “What are you looking for?”, “What would you do next?”, “What, if anything, is unclear?”
- Do not rescue until the task is abandoned or the participant asks
- Record assists, errors, hesitation, and scope-checking
- Capture task success, SEQ (or agreed ease item), confidence, time or steps if planned

## After each task

Ask only probes that serve an objective. Do not run a mechanical page-probe block on every screen.

Typical post-task: ease, confidence, “What do you think happened?”, “What would you expect next?”

## Sample

Roughly 4–8 participants per qualitative round is typical for discovering issues. That is **directional** for scores. Do not announce a precise Experience Score lift from five people. See [experience-metrics.md](experience-metrics.md).
